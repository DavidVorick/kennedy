History-ingress context management
==================================

This document records the discussion that led to the current
history-ingress context policy, the alternatives considered, and the final
decisions.


The original behavior
---------------------

A live conversation and its later history ingress share one Chatend journal.
When the source phase ended, the original ingress preparation treated almost
every active box the same way: it dehydrated ordinary boxes in bulk, then
rehydrated the system prompt and the two root-node boxes.

That policy was safe with respect to context capacity, but it threw away too
much useful working context. Most sessions are nowhere near the model's
context limit. Dehydrating an ordinary conversation merely because it crossed
the source/ingress boundary forced Kennedy to reconstruct information that
already fit comfortably.

The LoadNode overhaul made this especially obvious. Loaded Kweb context is now
a compact, globally deduplicated layout rather than a proliferation of
repeated boxes. Blanket dehydration was solving a size problem that normally
did not exist anymore.


Ideas considered
----------------

The first replacement proposal was a fixed allowlist:

- keep directly loaded, fixed, and active Kweb node boxes hydrated;
- keep user and Kennedy conversation messages hydrated;
- keep tool invocations hydrated, except for invocations longer than 1,000
  characters;
- dehydrate tool responses and everything else.

This protected the most important context but was still too eager. A
five-thousand-token conversation does not benefit from dehydrating a large web
result merely because history ingress began.

The next proposal used a nominal 600,000-byte ceiling, based on the rough
relationship between characters and tokens. That was better because it
preserved small sessions, but a fixed byte ceiling was wrong for models with
different context windows. It also duplicated information already available
from the selected model's advertised capabilities and Chatend's token
projection.

The final refinement recognized two kinds of summaries:

1. Kennedy-authored summaries are deliberate judgments about what matters in
   a box. They should always be reinstated for history ingress.
2. Programmatic summaries are mechanical space-saving representations. They
   should be created only when the context budget requires them.


The initial target and runtime budget
-------------------------------------

History ingress has an initial fitting target equal to:

    floor(model context window tokens * 75 / 100)

The context window is taken from the model actually selected for the ingress
call. It is not a fixed byte count and is not inherited blindly from an older
model selection. If the selected model changes, the budget changes with it.

Chatend compares its estimated projected token count with that target. The
projection includes box headers, continuation markers, the context footer,
and rendered box representations. Existing provider usage measurements may
calibrate the estimate.

Once ingress starts, hydration preflight and the agent loop use 100 percent of
the effective model window. Exceeding that full-window boundary force-commits
the staged transaction.


Ingress preparation order
-------------------------

Ingress preparation follows this order:

1. Terminate the source phase if it has not already been terminated.
2. Install the current history-ingress system prompt.
3. Record the current ingress model's effective context window and change the
   session kind to history ingress;
4. Revalidate loaded Kweb nodes against durable state.
5. Build an in-memory representation plan.
6. Append the final representation changes to the journal as one transition.
7. Record that history ingress has started.

The planner begins with this baseline:

- the ingress system prompt is hydrated;
- every box whose current representation is a Kennedy-authored summary keeps
  that summary;
- every other active box is tentatively hydrated.

Kennedy summaries are therefore used even when fully hydrating all canonical
content would fit. Kennedy has already identified the information that matters
in those boxes; history ingress does not second-guess that decision.

Only the current summarized representation is treated this way. If Kennedy
later rehydrated or dehydrated a previously summarized box, that later choice
is the active representation.

If the baseline projection is at or below 75 percent, no automatic dehydration
or programmatic summarization occurs.


Largest-first fitting
---------------------

If the baseline is too large, eligible boxes are ordered by their current
rendered token contribution, largest first. Because Kennedy summaries have
already been reinstated, a summarized box is ranked by the size of its
summary, not by the size of its canonical content. Box ID is the deterministic
tie-breaker.

The planner walks this ordering until the projected input is at or below the
75-percent target:

- an unprotected Kennedy-summarized box is dehydrated if the progression
  reaches it;
- a tool invocation longer than 1,000 characters receives a small
  programmatic summary if the progression reaches it;
- another eligible box is dehydrated.

The selected representation is retained even when a marker costs more than a
tiny box. This allows the final fallback to reach the required fully
dehydrated state deterministically.

Planning is hypothetical. The journal does not record a temporary
"rehydrate everything" pass followed by many corrections. Only the final
representation choices are appended, together, after the plan fits or every
box has been dehydrated.


Protected content
-----------------

These boxes are excluded from ordinary largest-first dehydration:

- the current system prompt;
- boxes named "User message" and owned by the user;
- boxes named "Kennedy message" and owned by Kennedy;
- Kweb boxes whose role metadata is "direct", "fixed", or "active";
- Kennedy tool invocations whose complete rendered canonical invocation is at
  most 1,000 characters.

The Kweb protection applies to every active full-node box in those roles. The
deduplicated LoadNode layout does not retain per-root attribution, and adding
such attribution solely for ingress would add complexity without improving
the intended result. Per-loaded-node fanout summaries and the three aggregate
Kweb summary boxes are not protected.

Protection applies during the first fitting pass. If protected content alone
cannot fit at or below 75 percent, those boxes are ordered by rendered size and
dehydrated largest-first too. If every box is dehydrated and the projection
is still above the target, the staged transaction commits immediately without
an ingress inference.


Programmatic tool summaries
---------------------------

Tool invocation boxes remain hydrated when the context fits. Even in an
oversized session, an invocation remains hydrated if larger reductions make
the context fit before the largest-first progression reaches it.

When the progression reaches an invocation longer than 1,000 characters, its
visible representation becomes a Chatend summary such as:

    Tool invocation: LoadNode {arguments dehydrated: 1,284 characters}.

The summary is deterministic and does not call an LLM. "Dehydrated" is used
instead of "omitted" to tell Kennedy that the canonical invocation is still
available through HydrateBox. The box is marked summarized, and its complete
canonical tool name and arguments remain in the append-only journal.

Tool results have no blanket special case. They are hydrated in a small
session and participate normally in largest-first dehydration in an oversized
session. In practice, this means very large web results, fetched pages, and
loaded code tend to be reduced first.


Attachment text
---------------

Previously, extracted attachment text was appended directly to the protected
User message box. A large document therefore became inseparable from the
conversation message and could not participate independently in context
fitting.

Each attachment's extracted text now receives its own user-owned box named:

    User attachment text: <filename>

The box is marked with attachment-text metadata but is not treated as a
conversation turn. Restoring the transcript selects only boxes named
"User message", so attachment text cannot become a duplicate user message
after restart.

The protected User message keeps the user's authored message and compact
object references. Inline data URLs and extracted text are removed from its
metadata. Raw attachment bytes remain staged journal objects and do not count
as rendered model context.

One box is created per attachment so a large document can be dehydrated
without hiding a smaller attachment or the user's actual message.


Timeout
-------

The native Codex AgentRequest defaults to ten minutes. Conversation turns
already overrode that default, but history ingress did not. History-ingress
agent turns now explicitly request a thirty-minute timeout.


Operational reset
-----------------

The two unfinished journals that predated these changes were intentionally
deleted without backup:

- be58e347-a251-4868-8a73-f3974ea4d20c.chatend
- 90263385-2241-4021-9a93-df84afc42830.chatend

The normal Session History API refuses to purge unfinished sessions by
design, so a complete development reset requires deleting the exact journal
files while the server is not running. No completed Kweb session history,
Kweb nodes, audio, or unrelated application data is part of that deletion.


Result
------

Ordinary sessions now enter history ingress with nearly all useful context
already visible. Kennedy's deliberate summaries are always honored. Automatic
reduction is reserved for sessions that genuinely approach the selected
model's capacity, and it normally affects only the largest expendable tool
results, attachment text, fetched pages, or code boxes.

Canonical content is never destroyed by summarization or dehydration. The
policy changes what is rendered to the model, not what the journal retains.
