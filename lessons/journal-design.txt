JOURNAL DESIGN: INVESTIGATION, DECISIONS, AND FINAL MODEL
========================================================

Purpose
-------

The Chatend journal is the local authority for one unfinished Kennedy session.
It exists so an in-progress source conversation, its history-ingress
continuation, pending browser commands, staged Kweb work, and attached objects
can be reconstructed after the server process restarts.

It is not the permanent conversation archive. When the session finishes, one
Kweb transaction stores the immutable session archive, accepted objects, and
node changes. Session History records the permanent archive object ID and the
in-progress journal is removed.

The journal contains more than the material rendered in the current model
context. It also contains:

- session metadata and lifecycle sidebands;
- ordered browser commands and their status;
- all Chatend events and canonical box revisions;
- hydration, dehydration, summary, retirement, and layout events;
- provider submissions and usage receipts;
- tool calls and results;
- the semantic Kweb plan and history-ingress progress;
- pending-node and pending-object allocations;
- raw staged-object records;
- Kweb finalization results.

Most of those records are not rendered as live history. They are retained
because replay needs them to reconstruct current state, history ingress may
inspect old events selectively, and finalization needs the staged Kweb plan and
objects.


What exposed the problem
------------------------

The first conversation after the overhaul entered history ingress before
Kennedy answered. That immediate ingress was caused by an oversized initial
context after the active/recent Kweb connection cap was accidentally removed.
The investigation then exposed a separate journal performance problem.

Refreshing the webpage asks Session History for conversation summaries and
command heads. Those paths independently open and replay every active journal.
Further hydration and the backend command poll can open them again. The
frontend does not render every journal event, but the old implementation still
materialized every event before producing a summary.

One active journal was about 7.5 MiB with roughly 440 transition records. A
warm open took about seven seconds even though rendering the resulting state
took less than a millisecond.


Why replay became quadratic
----------------------------

The old Chatend transition application used this pattern:

    clone the entire accumulated Chatend state
    apply the transition to the clone
    replace the original state with the clone

The clone grew after every frame. Replaying N similarly sized additions
therefore copied approximately:

    1 + 2 + 3 + ... + N

units of accumulated state. That is quadratic work. Event payloads, boxes,
pending resources, occurrence histories, and other materialized state were
copied repeatedly.

Live commits were worse: commit_events cloned Chatend into an outer candidate,
then apply_transition cloned that candidate again. Live commits also rebuilt
derived tool-slot state from all boxes.

The clone existed to give a transition in-memory transactional semantics. If
event 4 of a 6-event transition failed, the original Chatend would remain
unchanged. That was defensive database-style behavior applied to trusted local
events.


Why transactional in-memory application was rejected
-----------------------------------------------------

Journal events are constructed by local code. Callers validate user-facing
inputs and build event sequences before appending them. We do not need to treat
each local event as a hostile database transaction.

If a checksum-valid locally produced event violates Chatend invariants, that
is a programming or compatibility error. Cloning the complete session before
every transition is an expensive way to conceal such a bug.

Replay also does not need rollback. If semantic replay fails, SessionJournal
open returns an error and the partially built in-memory Chatend is dropped.

The final decision is therefore:

- apply events directly to Chatend;
- do not clone the accumulated state;
- do not roll back partially applied in-memory transitions;
- treat semantic failures in checksum-valid records as code/schema errors.

Tool-slot state is updated as the corresponding box creation and retirement
events are applied, rather than being reconstructed after every live update.


Final append-only record model
------------------------------

Every journal starts with:

    KCHAT01\n

Each following frame has:

- a one-byte frame kind;
- an eight-byte little-endian payload length;
- a 32-byte SHA-256 payload checksum;
- the payload.

JSON frames hold the session header, transitions, and sidebands. Raw-object
frames hold compact metadata followed by unencoded object bytes.

Normal JSON frames are assembled into one contiguous frame buffer and passed
to write_all. Journal files are opened in append mode. A per-path in-process
append lock remains so two SessionJournal handles cannot interleave frames.
That lock is ordinary writer coordination, not transaction or durability
machinery.

A record is the unit of recovery. Kernel write calls are not themselves the
atomicity mechanism. A write may stop partway through a frame; the frame's
length and checksum make the incomplete tail recognizable later.


Recovery rule
-------------

Opening a journal scans from the beginning in frame order.

For each frame:

1. Read the fixed header.
2. Verify that the declared payload fits in the file.
3. Compute and compare the payload checksum.
4. Decode and apply the checksum-valid payload directly to in-memory state.

At the first incomplete frame or checksum mismatch:

1. Stop replay.
2. Truncate the file at the start of that frame.
3. Discard that frame and every byte after it.
4. Leave the journal ready for later appends.

Later frames are discarded even if they happen to be individually valid.
They may depend on the rejected frame, so the only meaningful recoverable
state is the valid prefix.

Checksum-valid but structurally invalid data remains fatal. Examples include
unknown frame kinds, invalid JSON, an unsupported format version, duplicate
identities, or an impossible event sequence. Those cases indicate incompatible
software or a locally generated invalid record, not an interrupted append.

The same checksum-prefix rule applies to transitions, sidebands, and raw-object
frames.


Batching
--------

Batching remains, but it is only record grouping. It is not an ACID
transaction subsystem.

Transition already contains an ordered Vec<Event>. Operations build that
vector in memory, encode it once, and append one frame. One checksum therefore
covers the whole batch. On recovery the entire batch is either accepted or
discarded.

Current useful batches include:

- a stateful tool update that may create, rename, update, retire, and reorder
  several tool boxes;
- history-ingress preparation that dehydrates many boxes together.

Most operations naturally produce one event and therefore one single-event
transition. There is no cross-frame transaction and no reason to add one.


Durability decision
-------------------

The journal uses ordinary append I/O. It does not explicitly flush, call
sync_data or sync_all, fsync the parent directory, run a group-commit worker,
track dirty generations, or wait for a scheduled durability barrier before
finalization.

Once write_all succeeds, the operating system has accepted the bytes. Killing
the Kennedy process does not discard kernel page-cache writes. A sudden machine
power loss may lose or damage a suffix. The checksum-prefix recovery rule is
the accepted response to that risk.

This is intentionally weaker than a database durability guarantee. The
journal preserves restartable session state without pretending to be an ACID
database.

Unrelated systems keep their own contracts. Kweb still owns its transaction
log and WAL. Credential, backup, SQLite, audio, and completed-session catalog
sync behavior is not removed merely because the Chatend journal is simpler.


Performance result
------------------

Replay now performs one sequential checksum/decode/apply pass. It no longer
copies all previously accumulated state for each transition. Work is
effectively linear in journal bytes and event payloads, apart from ordinary
ordered-map lookup costs.

There are no compact state checkpoints and no journal index. The complete
valid log remains the authority and is replayed when a SessionJournal is
opened. This is intentionally simple.

The application still opens journals more often than an ideal long-lived
cache would require. Removing quadratic replay makes those opens inexpensive
for normal journals. Repeated opens and repeated large-object hashing are
separate possible optimizations, not reasons to reintroduce checkpoints or
transaction machinery.


Large objects
-------------

The V1 object strategy remains deliberately simple.

The browser uploads original File or Blob data as multipart bytes and receives
a session-local pending ID such as pending:47. The raw bytes are appended as
one logical object frame. Later message boxes and staged Kweb node operations
refer to the pending ID rather than embedding the payload in JSON or model
context.

An object frame checksum covers its event prefix, metadata, and complete raw
body. Object frames may be written with several write_all calls under the
append lock. Building a second object-sized buffer solely to force the header
and a potentially huge body into one call would waste memory and would not
improve the recovery contract.

On replay, the object body is hashed with a bounded scratch buffer. Only its
metadata, byte offset, and byte length remain in memory. If the object frame is
bad, it and all later records are discarded. Because an object is staged
before a message can refer to it, this also discards any later reference and
avoids a dangling pending ID.

At finalization, the current implementation reads all staged objects into
memory and passes Vec<u8> values to the existing Kweb transaction API. Kweb
writes them into its immutable object store and returns canonical object IDs,
which replace pending IDs in committed node data. This performs one disk write
to the Chatend journal and a second disk write to Kweb.

The advertised V1 limits are 32 GiB for one object and 32 GiB aggregate, but
the implementation is not end-to-end streaming:

- the multipart endpoint buffers a complete upload;
- interrupted uploads cannot resume;
- finalization holds all staged object bytes in memory;
- the Kweb object API accepts Vec<u8>, not a reader or file range;
- reopening a journal hashes every object body;
- clearing a browser attachment draft does not unstage the already appended
  object, and finalization currently commits every staged object.

True streaming, chunked retry, range access, and zero-copy Kweb file adoption
are explicitly deferred. The journal simplification does not attempt to solve
them.


Compatibility and scope
-----------------------

The on-disk KCHAT01 frame format did not need a version change. Existing valid
journals remain readable. The behavior change is that a checksum mismatch now
recovers the preceding valid prefix instead of making the complete journal
unopenable.

The implementation changes are intentionally confined to:

- Chatend transition application, append handling, recovery, and tests;
- callers that waited for SessionJournal::sync_all;
- journal-specific documentation and durability claims.

No compact checkpoints, background committer, rollback state, prepared
transaction package, streaming object protocol, or frontend save-state UI was
introduced.


Tests that define the contract
------------------------------

The journal tests cover:

- normal state and object replay;
- incomplete-tail truncation followed by resumed appending;
- checksum mismatch truncation with valid-looking later frames discarded;
- all-or-nothing recovery of a multi-event transition;
- object checksum mismatch discarding the object and later frames;
- incremental tool-slot reconstruction during replay.

The central lesson is that the checksum boundary already provides the only
atomic recovery property this trusted local append log needs. Copying the
entire state, rolling back in-memory event application, and scheduling fsync
transactions added substantial complexity and quadratic cost without serving
the chosen failure model.
