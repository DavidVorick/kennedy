# History Event Log

## Purpose

The history event log is the complete durable record of a Kennedy conversation. It preserves every message, tool interaction, canonical box revision and Kennedy transformation needed to reconstruct both:

- the fully hydrated source history;
- the exact active context Kennedy saw at any inference.

The log is append-only. Context assembly, dehydration and summaries create projections or new events; they never rewrite prior history.

## Event Sequence

Every action receives a unique monotonically increasing `EventId`. Event order is authoritative; timestamps are supplemental metadata.

A box’s `BoxId` is the `EventId` of the event that created it. Later events reference that stable box ID.

For example:

- Event 14 creates Box 14.
- Event 31 updates Box 14.
- Event 47 records Kennedy summarizing Box 14.
- Event 63 retires Box 14.

Every event may link to the preceding event for the same box, producing an exact per-box revision chain.

## Event Record

An event contains enough information to establish:

- its `EventId`;
- event type;
- actor or source;
- affected `BoxId`, when applicable;
- preceding event for that box;
- canonical revision or representation lineage;
- exact payload or exact object reference;
- associated tool invocation, when applicable;
- chronological timestamp and session identity.

Large payloads need not be stored inline. An object-backed event must retain a reference sufficient to recover the exact original bytes. Referenced history objects remain available for as long as the event log exists.

## Event Types

### Message Created

Records a user or Kennedy message, its role, source and exact contents. The creation event also creates its message box.

A later source edit is a canonical update to the same message box rather than a replacement of history.

### Tool Invoked

Records the exact tool instance, method and arguments supplied by Kennedy.

### Tool Completed

Records success, failure or ambiguity and associates the result with its invocation.

A legacy completion creates one result box. A stateful completion records the complete accepted slot transition and the individual box events it caused.

### Box Created

Creates one logical box. Its event ID becomes its stable box ID.

### Canonical Updated

Adds a canonical revision owned by the box owner. It preserves the prior revision and records the exact changed state.

If Kennedy was using an override, the event also records that the visible representation remained compact and became dirty.

### Kennedy Replaced

Records Kennedy replacing a box’s visible representation with Kennedy-authored text.

A summary event identifies the box and canonical event being summarized. Its text is retained exactly and may later be hydrated independently of the source.

### Box Blanched

Records Kennedy replacing the visible representation with no substantive contents. Identity and lineage remain present.

### Box Restored

Records Kennedy restoring a selected canonical representation, ordinarily the latest canonical revision.

### Box Retired

Records the owner removing the box from live context. Retirement preserves all earlier canonical and Kennedy-authored events.

### Ingress Summary

Records a summary authored during history ingress. It identifies the events or ranges it covers and is itself an ordinary historical event that may later be hydrated or dehydrated.

## Box Occurrences

A box may have many chronological occurrences while retaining one identity.

The event log stores the actual events, not destructive edits to old occurrences. Context assembly deterministically renders an earlier occurrence as an immutable continuation marker when a later event becomes the box’s current occurrence.

For example:

`Box 14 continued at Event 31.`

These markers are derived from the event chain. Rendering them does not mutate Event 14.

Movement does not determine hydration. A later occurrence may contain full canonical text, a Kennedy summary or a blank representation depending on Kennedy’s active-view decision.

## Exact Reconstruction

Replaying events in order reconstructs:

- every box and canonical revision;
- every stateful tool slot transition;
- which boxes were active or retired;
- every Kennedy summary, blanch and restore;
- which representation was visible at each event;
- the complete request projection used for each inference.

No assembled prompt snapshot needs to be duplicated if it can be reproduced exactly from the event log and its referenced objects.

Provider receipts, including observed input-token usage, may be attached to the corresponding inference event.

## Historical Hydration

History ingress may request any historical occurrence by `EventId`.

Hydrating an event restores the exact box representation associated with that moment:

- a canonical payload for a source event;
- a historical Kennedy summary for a summary event;
- a blank state for a blanch event;
- the selected canonical revision for a restore event.

The event’s lineage permits ingress to move between a summary and the canonical source it described.

Hydration affects only the current history-ingress view. It does not change the original event log.

## Dehydrated Projection

A fully dehydrated history contains every event in chronological order but replaces large payloads with compact metadata:

- event and box IDs;
- event type and source;
- revision and lineage;
- lifecycle state;
- estimated hydration cost.

This complete skeleton is the starting context for history ingress.

## Durability and Invariants

- Events are appended before their resulting state is treated as durable.
- Event IDs, box IDs and historical payloads are never reused.
- Accepted events are never edited or deleted.
- Every canonical and Kennedy-authored representation remains recoverable.
- Continuation markers are derived and never rewrite history.
- Object-backed payloads retain exact lineage.
- Failed tool transitions do not create successful box-state events.
- Replaying the complete log yields the same canonical and active historical states.
