CHATEND OVERHAUL DISCUSSION REVIEW
==================================

Status: Ongoing
Started: 2026-07-23

Purpose
-------

This file is the running narrative review of the architecture discussion for
the Chatend overhaul. It records the questions raised, the reasoning behind
them, and especially the decisions reached. It is intentionally separate from
chatend-overhaul-clarifications.md:

- chatend-overhaul-clarifications.md is the concise authoritative requirements
  document.
- this file preserves how and why those requirements were chosen.

New discussion entries should be appended. Earlier entries should not be
silently rewritten merely because a later decision supersedes them; the later
entry should identify the supersession.


ENTRY 1: INITIAL ARCHITECTURE REVIEW
------------------------------------

The existing context-box proposal was reviewed against Kennedy's newly
migrated kcode-kweb-db backend.

The review concluded that this is not merely a browser frontend redesign. It
replaces substantial parts of Chatend, Conversation History, backend
orchestration, provider rendering, object custody, history ingress, and Kweb
transaction construction.

The Kweb migration remains a valid foundation:

- committed Kweb nodes and objects have canonical eight-character IDs;
- current state and native history use kcode-kweb-db;
- exact duplicate signed transactions are accepted as successful no-ops;
- one Kennedy writer is provisioned in the encrypted vault.

The first implementation questions identified were:

1. How session objects are staged and eventually handed to Kweb.
2. How nodes and objects created during a staged history-ingress plan are
   addressed before the final Kweb transaction exists.
3. How in-progress event, box, provider, tool, and object state survives
   restart.
4. Where the session archive ends, given that an object cannot contain its own
   final Kweb object ID.
5. Whether Kweb-writing sessions are serialized or allowed to stage against
   concurrently changing nodes.
6. How system prompts, tool definitions, continuation markers, stale
   representations, and context limits appear to Kennedy.
7. What happens to legacy active and completed sessions at cutover.


ENTRY 2: FIRST SET OF STORAGE AND EXECUTION DECISIONS
-----------------------------------------------------

Object staging
~~~~~~~~~~~~~~

The user decided that V1 should prefer the simpler existing Kweb object API
even though it writes bytes twice:

1. Chatend first persists accepted object bytes locally as part of the
   recoverable in-progress session.
2. At final session commit, Kennedy reads those bytes and supplies them through
   the normal kcode-kweb-db transaction API.
3. Kweb writes the accepted object into its permanent object store.

Avoiding the second disk write is not worth complicating the Kweb API during
V1. A staged-file adoption or zero-copy handoff may be added after the overall
system matures.

Temporary IDs
~~~~~~~~~~~~~

One monotonically increasing session-local temporary-identity counter is shared
by boxes, pending Kweb nodes, and pending Kweb objects. Allocating any of those
consumes the next number, so numeric temporary IDs do not overlap.

Pending resources use compact identifiers such as:

    pending:47

Committed Kweb resources continue to use canonical eight-character IDs.
Pending references are resolved while the final real Kweb transaction is
constructed.

In-progress representation
~~~~~~~~~~~~~~~~~~~~~~~~~~

The user deliberately chose JSON for rapidly evolving Chatend state. Binary
Kweb formats need canonical stability, but Chatend fields are expected to
change frequently in response to feature requests. Additive JSON fields make
those changes much easier to deploy and recover.

Each in-progress session is stored independently and append-only until its
history ingress and Kweb commit finish. Session objects remain local during
this period.

Completed-session discovery
~~~~~~~~~~~~~~~~~~~~~~~~~~~

The local Session History domain keeps a small file containing the permanent
Kweb object IDs of committed session archives. The complete session is not
duplicated locally. Opening a historical session loads its immutable object
from Kweb.

The session object does not contain its own object ID. Kweb allocates the ID
during final transaction construction, and Kennedy records it locally after
commit. Therefore the archive has no self-referential ID problem.

Kweb writer lane
~~~~~~~~~~~~~~~~

V1 has one global Kweb write lane:

- history ingress is read-write and acquires the lane;
- self time is read-write and acquires the lane before loading nodes;
- any other Kweb-writing session type uses the same lane;
- only one such session runs at a time;
- read-only sessions and Kweb reads remain fully parallel.

When a previously read-only session terminates and enters history ingress, it
revalidates nodes loaded during the source session. Nodes changed since their
original load produce system-authored update material. These updates start
dehydrated, and Kennedy chooses whether to inspect them.

System and tool boxes
~~~~~~~~~~~~~~~~~~~~~

System prompts are persisted boxes and are part of the complete session.
Kennedy controls their active representation. Critical instructions, including
Ktool use, are supplied through system-prompt boxes.

If one Kennedy response invokes several tools, each invocation is recorded
independently and owns its own resulting boxes. Their application follows the
provider's actual invocation order.

Only Kennedy manages active box representations. The user interface is an
observer and communication surface, not a second context editor.

Context budgets
~~~~~~~~~~~~~~~

Source sessions are limited to 70 percent of the selected model's effective
context window. The remaining capacity allows the later history-ingress phase
to hydrate sources, reason, call tools, and author summaries.

An expansion that would exceed the applicable limit is rejected with a visible
capacity error. If even that error cannot fit without taking a source session
over 72 percent, the source session is forcibly terminated and queued for
history ingress.

History ingress may use the full effective context window.

Self-time handoff
~~~~~~~~~~~~~~~~~

ResetContext disappears. Self time retains the existing ability to leave one
message for the next self-time session. General session segmentation and
multi-agent handoff frameworks are deferred.

Legacy cutover
~~~~~~~~~~~~~~

Open legacy sessions are not converted into synthetic box history. Each is
exported as a complete text file under data/archive/unfinished-sessions/ for
manual ingress.


ENTRY 3: REPRESENTATION TERMINOLOGY AND FINALIZATION DECISIONS
--------------------------------------------------------------

Continuation markers
~~~~~~~~~~~~~~~~~~~~

Continuation markers remain in Kennedy's active context. When a box receives a
later occurrence, the earlier occurrence becomes a compact immutable pointer to
the next event. This gives Kennedy a useful view of how context evolved without
repeating the full earlier payload.

Hydrated, dehydrated, summarized, and stale
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

The old words "blanched" and "dirty" are retired.

- Hydrated means the selected contents are present in active context.
- Dehydrated means the substantive contents have been pulled out while compact
  identity and restoration information remain.
- Summarized means Kennedy replaced the source contents with Kennedy-authored
  text.
- Stale means a dehydrated or summarized representation is based on an older
  canonical revision.

Only Kennedy normally changes hydration or summary state. The one automatic
controller dehydration happens when a terminated source session is prepared
for history ingress.

History-ingress bootstrap
~~~~~~~~~~~~~~~~~~~~~~~~~

When history ingress begins:

1. The terminated source session is automatically dehydrated.
2. The history-ingress system-prompt boxes are explicitly hydrated.
3. Kennedy's Kweb root and the user's Kweb root are explicitly hydrated.
4. Revalidation notices for Kweb nodes changed since their source-session load
   begin dehydrated.

This ensures that ingress starts with instructions and navigation anchors even
if Kennedy dehydrated critical prompt material during the source session.

One physical in-progress file
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

The user requested one file per unfinished session and delegated its internal
layout.

The selected V1 interpretation is a simple append-only framed journal:

- event and transition payloads are JSON;
- large object payloads are raw binary records, avoiding Base64 expansion;
- one accepted atomic transition is one JSON journal record containing its
  ordered events;
- object metadata and later events refer to raw records by pending ID and
  location;
- complete records are flushed and fsynced before acknowledgment;
- restart accepts complete records in order and discards only an incomplete
  final frame.

The small framing envelope is stable; rapidly evolving Chatend schemas remain
JSON.

Exact transaction retry
~~~~~~~~~~~~~~~~~~~~~~~

Before Kennedy calls Kweb, the exact signed transaction and everything needed
to reconstruct its object payloads are persisted and fsynced in the session
journal.

If Kennedy crashes during submission, restart submits the identical signed
transaction again. kcode-kweb-db recognizes the transaction ID and returns
success without processing it twice.

This is distinct from staged-file object adoption. V1 still accepts the second
disk write for objects.

Permanent session contents
~~~~~~~~~~~~~~~~~~~~~~~~~~

The permanent session history object may continue to use session-local pending
IDs. It does not need a table translating every historical mention to the
canonical IDs allocated at final commit.

The local completed-session file is only the user-requested list of permanent
session object IDs. A richer metadata index is not required for V1.

History ingress at capacity
~~~~~~~~~~~~~~~~~~~~~~~~~~~

History ingress has no output reserve and may use 100 percent of the effective
window. If it reaches that ceiling and can no longer make progress, it ends at
its current state and Kennedy commits the staged work completed so far as the
session's one Kweb transaction.

Object memory limit
~~~~~~~~~~~~~~~~~~~

V1 retains the existing 32 GiB Kweb limit. Kennedy does not impose a smaller
RAM-safety limit. Deployment machines have substantially more memory than the
maximum transaction object payload.

Legacy records
~~~~~~~~~~~~~~

All legacy sessions, completed as well as unfinished, will be archived and
removed from live persistence at overhaul cutover. The archives are intended
to be moved off-machine. The new runtime will contain no legacy session loader
and will not maintain legacy compatibility code.


CURRENT OPEN IMPLEMENTATION QUESTION
------------------------------------

The exact retry requirement needs a way to obtain the signed transaction before
it is committed. The current kcode-kweb-db local Transaction::finalize method
constructs and commits internally.

This does not require the rejected zero-copy object handoff. It likely requires
only a small transaction-preparation API that:

1. consumes a locally built Transaction;
2. returns its exact signed transaction package without committing it;
3. allows Kennedy to persist and fsync that package;
4. allows KwebDb::accept_transaction to submit or resubmit it.

Alternatively Kennedy would have to duplicate kcode-kweb-db's canonical wire
encoder and signing rules, which would be fragile and is not recommended.

This API point remains to be confirmed in the next discussion entry.


ENTRY 4: V1 SIMPLICITY DECISIONS AND DESIGN CLOSURE
---------------------------------------------------

Prepared transaction packages deferred
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

The user decided not to add Transaction::prepare or another
TransactionPackage-producing API in V1.

Kennedy will persist and fsync the complete local session and staged transaction
plan, then use the current Kweb transaction builder and finalize method. There
is consequently a brief crash window in which Kweb may have committed while
Kennedy has not yet recorded local completion. Because the current API cannot
reconstruct the byte-identical signed transaction after restart, V1 accepts the
small possibility of an unknown outcome, duplicate reconstructed transaction,
or related corruption. Exact persisted-package resubmission is a future
hardening optimization.

This decision is deliberate. It keeps both the Kennedy adapter and
kcode-kweb-db API smaller while the much larger Chatend model is still
maturing.

Stale boxes stay simple
~~~~~~~~~~~~~~~~~~~~~~

A stale dehydrated or summarized box does not contain a generated explanation,
diff, or summary of what changed.

When a loaded Kweb node advances before history ingress:

1. the canonical box revision advances;
2. the retained dehydrated or summarized representation is marked stale;
3. its system-authored update occurrence identifies the affected box;
4. Kennedy hydrates the box if she wants to inspect the new canonical contents.

The controller does not spend context attempting to anticipate which changes
Kennedy will care about.

Provider tool bridge
~~~~~~~~~~~~~~~~~~~~

The provider-level call_ktool function remains registered for every Kennedy
inference. Its detailed operating instructions are still contained in
system-prompt boxes and may be dehydrated by Kennedy. Dehydrating the
instructions does not unregister the transport-level function.

Readiness conclusion
~~~~~~~~~~~~~~~~~~~~

With these decisions, the remaining questions are implementation details rather
than unresolved product architecture. The authoritative clarifications now
cover:

- session boundaries and one-session/one-transaction permanence;
- box identity, continuation, hydration, summaries, and stale state;
- one-file append-only in-progress persistence;
- temporary IDs and final Kweb allocation;
- local object staging and accepted V1 disk duplication;
- the accepted finalization crash window;
- the global Kweb write lane and read concurrency;
- history-ingress revalidation and bootstrap state;
- source and ingress context ceilings;
- system prompts, call_ktool, and Kennedy-only context control;
- completed-session object discovery;
- self-time handoff;
- legacy cutover with no compatibility loader;
- the 32 GiB V1 object and transaction-payload ceiling.

The design discussion is ready to transition into an implementation plan and
code changes.


ENTRY 5: IMPLEMENTATION AND CUTOVER OUTCOME
-------------------------------------------

The full overhaul was implemented on 2026-07-23.

The final code follows the decisions above:

- Chatend is now an append-only checksummed journal with one shared ID space,
  durable boxes, continuation events, canonical revisions, hydration,
  dehydration, summaries, and stale state.
- System prompts, messages, tool calls, tool results, Kweb nodes, and
  controller notices are boxes.
- Provider requests are rebuilt from the current projection, and call_ktool
  remains registered independently of prompt-box hydration.
- Kweb writes remain staged until the one global writer lane completes the
  session's single transaction.
- Staged node creates and updates immediately update Kennedy's Kweb boxes, so
  read-your-writes behavior does not depend on the permanent commit.
- Browser objects are raw multipart uploads staged in the journal. V1 accepts
  the second disk write at Kweb commit.
- Session History lifecycle and command records are sidebands in the same
  journal. Completed local history is only an fsynced list of permanent Kweb
  archive object IDs.
- The frontend displays boxes and resolves completed Session History detail
  from Kweb.
- Crossing the 72 percent emergency boundary ends a source session and queues
  the same journal for history ingress.
- Backup format 10 includes active journals and the permanent ID list.

The deliberate V1 transaction-finalization window remains exactly as agreed.
The implementation fsyncs the journal and full semantic Kweb plan before
calling the library. It does not claim that a crash after Kweb commit but
before the local completion event can reconstruct the byte-identical signed
transaction.

Legacy cutover result
~~~~~~~~~~~~~~~~~~~~~

The stopped live data was cut over after implementation:

- 6 unfinished legacy sessions were exported into separate text files;
- the complete 4,158,308,352-byte legacy conversation database and sidecars
  were moved to data/archive/legacy-sessions-2026-07-23T10-16-35Z/;
- all 67 legacy conversation rows in the mixed memory-ingress queue were
  copied into a separate 1,341,689,856-byte archive database and count-checked
  before deletion from the live queue;
- data/sessions/in-progress/ and data/session-history.txt were initialized;
- no live kennedy-conversations.sqlite3 remains and there is no legacy loader.

Verification
~~~~~~~~~~~~

The implementation is verified by Rust workspace tests, Chatend replay and
frame-recovery tests, Session History tests, Kweb single-session transaction
tests, backend orchestration tests, JavaScript syntax checks, and the browser
MVP test suite.

Final storage audit
~~~~~~~~~~~~~~~~~~~

The post-implementation audit made two additional corrections required by the
agreed design:

- provider input-token receipts now recalibrate the exact matching inference
  manifest, and later estimates apply text deltas to that measured baseline;
- reopening a journal verifies staged-object checksums as a bounded streaming
  read instead of allocating the complete object in memory.

Journal creation, completed-ID-list creation, and committed-journal removal
also fsync their containing directories so acknowledged files and removals
survive a machine restart rather than only a process restart.
