# Controller Lifecycle and Interfaces

## Purpose

This document specifies the controller behavior connecting boxes, tools, provider inference, durable history and user-facing conversation history.

The controller owns orchestration and persistence. It does not decide which source material Kennedy should consider important.

## Distinct Views

The system maintains four related views:

### Canonical State

Contains the latest owner-controlled contents of every active or retired box. Stateful tools operate against this view and never see Kennedy’s private transformations.

### Kennedy Active View

Contains the chronological event skeleton plus each active box’s Kennedy-selected representation. This is assembled into provider input.

### Durable Audit View

Contains exact messages, tool calls, outcomes, canonical revisions, Kennedy transformations and object lineage. User interfaces may display this complete history even when Kennedy has blanched parts of her active view.

### History-Ingress View

Begins as the complete dehydrated audit history and selectively hydrates exact historical events.

Changing one view never silently changes another.

## Kennedy Operations

Live Kennedy has three one-box operations:

- **Replace:** install arbitrary Kennedy-authored text, including a summary.
- **Blanch:** retain only the compact identity and lineage marker.
- **Restore:** reveal the latest canonical revision.

Each operation targets one `BoxId` and creates an event.

History-ingress Kennedy additionally has:

- **Hydrate Event:** reveal the exact representation associated with one `EventId`.
- **Dehydrate Event:** return that occurrence to its compact historical form.
- **Insert Summary:** append a Kennedy-authored derivative covering identified source events.

Live restoration uses a box ID because it normally wants the latest source. Historical hydration uses an event ID because it must recover a precise moment.

`ResetContext` and `UnloadNode` are not part of this model.

## Serialized Session State

Each logical session has one serialized event writer. Box creation, owner updates, Kennedy transformations, tool transitions and inference records are committed in one authoritative order.

Every operation applies to a fixed current state. A result associated with another tool instance, invocation or session cannot update the current boxes.

A stateful tool transition affecting multiple slots is accepted as one complete transition or rejected without partial box changes.

## Turn Lifecycle

A normal turn follows this sequence:

1. Append the exact user message or source edit.
2. Apply any resulting canonical box changes.
3. Assemble one fixed Kennedy-view snapshot.
4. Record the inference manifest.
5. Send the assembled request to the selected provider.
6. Record the provider output and usage receipt.
7. If Kennedy calls a tool, record the exact invocation.
8. Apply the tool outcome and box transition.
9. Reassemble context and continue until Kennedy produces a terminal response.
10. Preserve the completed event sequence for history ingress.

A source edit updates the existing message box rather than pretending the original event never occurred.

## Inference Manifest

Every provider inference records a compact manifest sufficient to reconstruct what Kennedy received.

The manifest identifies:

- provider and model revision;
- ordered current box occurrences;
- representation event or canonical revision for each occurrence;
- continuation-marker rendering version;
- active tool definitions and revisions;
- context-controller version;
- estimated input tokens;
- actual provider usage when returned.

Large contents are referenced rather than duplicated. The event log plus manifest and retained objects must reproduce the same semantic request without storing another full prompt snapshot.

## Provider and Role Rendering

The provider adapter converts ordered boxes into the provider’s required message and tool structure.

It must preserve:

- source role and authorship;
- tool-call/result pairing;
- chronological event order;
- Kennedy-summary derivative labels;
- the volatile dirty-box and budget footer.

Kennedy-authored text must never be rendered as if a user or external tool authored it.

Provider-specific framing may differ, but box identity and history semantics remain provider-independent.

## Durability and Objects

An event referencing an object is not durable until the exact object is recoverable. Object contents are saved before the referencing event is committed.

Accepted events are durable before their resulting state is treated as complete. After restart, the controller reconstructs:

- box and event identities;
- canonical revisions;
- active representations;
- tool-slot mappings;
- dirty and retired states;
- chronological continuation chains;
- inference manifests and object references.

A restart must not duplicate an accepted event or silently discard a completed transition.

## Failure Behavior

If context assembly, persistence, provider dispatch or a tool transition fails:

- prior committed box state remains valid;
- no partial representation is presented as complete;
- the failure is recorded with its associated operation;
- retries do not invent new successful effects;
- Kennedy receives a compact actionable error when continuation is possible.

Provider clipping is not a context-management mechanism.

## Session Boundaries

A fresh session is required when the dehydrated event skeleton approaches the configured effective-context ceiling. The new segment links to its predecessor so history remains continuous and exactly recoverable.

Fresh sessions are lifecycle boundaries, not substitutes for ordinary blanching and restoration.

Multimodal rendering, parallel Kennedy fleets, automatic semantic ingress prioritization and cross-agent box coordination remain outside V1.

## Invariants

- Canonical, active, audit and ingress views remain distinct.
- Every inference binds to one reconstructible context snapshot.
- Every accepted mutation has one authoritative chronological position.
- Tool and provider results update only their originating session state.
- Kennedy transformations affect visibility, never source truth.
- User-facing history remains complete even when Kennedy’s view is compact.
- Restart and session rollover preserve exact lineage.
