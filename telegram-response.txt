# Kennedy Architecture Direction for `kcode-tg-kennedy-bot`

## Executive direction

Add native Telegram photos, videos, animations, audio tracks, video notes, and stickers, but implement the smallest complete transport contract.

Do **not** implement the proposal verbatim. In particular:

- Do not add width, height, performer, title, `isAnimated`, or `isVideo` fields without a demonstrated consumer.
- Do not build a generic provider-metadata framework.
- Do not add a durable delivery outbox, guaranteed-delivery machinery, a store/facade rewrite, Kmap logic, model logic, or an object store.
- Do not add new public `Config` fields.
- Do not silently send native media as documents.
- Do not duplicate six largely identical media pipelines.
- Do not fetch remote source when the canonical managed 0.2.0 tree is available.

The relay should remain a small Telegram transport and transport archive. The host decides how media is retained downstream, interpreted, transcribed, described, exposed to Kennedy, or ignored.

Alongside native media, fix three concrete weaknesses in 0.2.0:

1. Move every `IdentitySink` callback outside SQLite mutex critical sections.
2. Add simple bounded transient Telegram retries—five total attempts, no durable outbox.
3. Preserve existing and new media metadata in passive group-ingress snapshots, which currently collapse media messages into text-only records.

These should be coherent, independently checkable checkpoints rather than one giant unbisectable rewrite.

---

## 1. Governing design principles

### 1.1 Keep the public boundary small

Every route, field, enum value, mode, promise, and error condition creates permanent maintenance and model-context cost.

Native media requires:

- recognizing Telegram’s native media kinds;
- preserving bounded provider bytes and essential metadata;
- exposing those bytes through the existing retrieval routes;
- sending through the correct native Telegram method;
- retaining existing authorization, binding, reply, archive, and completion behavior.

It does not require mirroring every Telegram media property into the Kennedy API.

### 1.2 Preserve transport ownership

The relay owns:

- Telegram polling and provider interaction;
- transport authorization checks;
- bounded media download and temporary durable transport storage;
- Telegram-native media classification;
- event and group-message association;
- event binding and completion fencing;
- transport archives and provider message IDs.

The relay does not own:

- Kmap roots or Kweb objects;
- prompts or model execution;
- transcription or visual understanding;
- application capabilities;
- long-term object-storage policy;
- semantic extraction;
- delivery to audiences other than the current Telegram transport destination.

### 1.3 Prefer availability to elaborate delivery guarantees

This is an informal chatbot transport.

- One poison message must not freeze everyone.
- Independent principals must remain isolated.
- Plausibly transient operations may receive at most five total attempts.
- Permanent failures stop immediately.
- Ambiguous sends may duplicate if retried; document that honestly.
- Do not introduce a durable outbox or exactly-once claim.

### 1.4 Preserve fail-closed group security

For quarantined groups, return before:

- inspecting caption or media content;
- selecting photo variants;
- downloading files;
- storing bytes or content metadata;
- parsing invocations;
- producing feedback;
- exposing anything to Kennedy.

Sender and membership envelope processing needed to maintain the security ledger remains allowed.

### 1.5 Keep lifecycle claims truthful

Keep these distinct:

- source changed;
- source checked;
- version selected;
- package published;
- consumer adopted;
- database migrated;
- service deployed;
- live Telegram behavior verified.

Publication requires separate authority.

---

## 2. Recommended checkpoint sequence

Use the next available versions rather than assuming these exact numbers are unused.

### Checkpoint A: 0.2.x concurrency-boundary repair

Move all host callbacks outside SQLite mutex ownership and add deterministic tests proving it.

### Checkpoint B: 0.2.x bounded Telegram retries

Add one centralized retry policy and apply it to appropriate existing operations.

### Checkpoint C: 0.2.x group media-fidelity repair

Make passive background-ingress snapshots preserve the same media metadata already present in ordinary group context. Extend media preparation to existing media kinds consistently.

### Checkpoint D: next minor release, likely 0.3.0

Add native media kinds, the native outbound route, retrieval support, capability discovery, migration, documentation, and tests.

If publication is authorized, publish each clean coherent checkpoint before beginning the next independent change. Do not accumulate all four into one release merely to avoid version increments.

# Part I — Required 0.2.0 hardening

## 3. Remove host callbacks from SQLite critical sections

The current source still calls `IdentitySink` methods from paths holding the shared SQLite mutex, especially group creation, membership processing, and group validation.

This violates principal isolation: a slow host callback can serialize unrelated Telegram workers and local API requests.

### Required rule

Never hold the SQLite mutex while calling:

- `observe_identity`;
- `whitelist`;
- `request_add_user`;
- `observe_group`;
- Telegram;
- another host callback;
- sleep or retry backoff;
- media download;
- large computation.

### Implementation pattern

Use a short staged flow:

1. Read or compute only the minimum local state needed.
2. Release the database lock.
3. Invoke the host or Telegram.
4. Reacquire the lock.
5. Apply one short mutation or compare-and-swap transition.
6. Release immediately.

Where group creation returns a new or existing stable `group_id`, call `observe_group` after releasing the database lock. The observation callback should remain safely repeatable.

Obtain a `WhitelistSnapshot` before entering the short eligibility transaction. Evaluate and persist the group decision against that point-in-time snapshot.

Do not undertake a broad database actor, connection pool, or storage rewrite in this branch. First remove known long external work from the lock and measure the remaining SQLite operations.

### Tests

Add deterministic tests proving:

- a blocked `observe_group` callback does not hold the database mutex;
- a blocked `whitelist` callback does not prevent an unrelated database operation;
- no group authorization decision is made without a current whitelist snapshot;
- callbacks may fail without corrupting transport state;
- repeated `observe_group` calls remain harmless.

Do not use a flaky wall-clock “under 200 ms” assertion in normal CI. Use gates/channels to prove overlap deterministically, with a separate benchmark or ignored performance test for real latency.

---

## 4. Add bounded transient retries

Version 0.2.0 classifies Telegram errors safely, but most user operations still make a single attempt. Add one small shared retry mechanism rather than separate retry loops throughout the code.

### Policy

- Maximum: **five total attempts**, including the first.
- Retry only errors known to be plausibly transient.
- Stop immediately on permanent Telegram API errors, invalid input, authorization failure, SQLite failure, or host callback failure.
- Respect Telegram `RetryAfter`.
- Use a small bounded backoff for timeout/connect/network failures.
- Do not add a retry dependency solely for this.
- Never log raw `RequestError`, `DownloadError`, URLs, request bodies, captions, filenames, or token-bearing provider output.
- Log only the existing nonsecret error class, attempt number, operation class, and safe transport identifiers.

### Appropriate retry targets

Apply the helper to bounded operations such as:

- startup `getMe`;
- Telegram sends;
- `getFile`;
- media download restart;
- group-membership provider reads;
- other idempotent Telegram metadata reads.

### Ambiguous sends

A network failure may occur after Telegram accepted a send but before the client received the response. Retrying may duplicate the message.

That is acceptable for this informal transport, but must be documented. Do not claim duplicate-free delivery and do not add an outbox.

### Polling exception

Long polling is a continuous service loop, not one finite user operation. It may continue attempting future polls after failures. Do not stop Telegram polling forever after five lifetime failures.

Keep the distinction explicit:

- one bounded operation: at most five total attempts;
- long-lived poller: continue operating, with bounded delay per failed cycle.

### Tests

Cover:

- transient failure followed by success;
- five transient failures followed by abandonment;
- permanent API failure making exactly one attempt;
- `RetryAfter`;
- ambiguous send behavior documented and surfaced;
- retry exhaustion for one principal not blocking another;
- logs containing no raw token or Bot API URL.

---

## 5. Repair group background-ingress media fidelity

Current group session/context JSON carries media metadata, but `maybe_queue_group_ingress` and edit-time snapshot refresh serialize only text-oriented fields. This means passive voice and document messages can become semantically invisible in background-ingress batches.

Fix this for existing media before adding more kinds.

Every group-ingress message object should additively include:

- `kind`;
- `mimeType`;
- `fileName`;
- `durationSeconds`;
- `preparedText`;
- `preparationModel`;
- `documentFormat`;
- `preparationTruncated`;
- `hasMedia`.

Retain all existing fields and exact text behavior.

Use one shared row-to-JSON helper for:

- recent group context;
- group-session updates;
- background-ingress creation;
- pending background-ingress refresh after edits.

Do not maintain several subtly different media projections.

Extend `POST /api/v1/group-messages/{chat_id}/{message_id}/preparation` to accept every retained media kind, including the native kinds added later. It remains a host-supplied preparation record; the relay must not perform extraction itself.

# Part II — Native media expansion

## 6. Supported native kinds

Add these transport kind strings:

- `photo`
- `video`
- `animation`
- `audio`
- `video_note`
- `sticker`

Retain unchanged:

- `text`
- `voice`
- `document`
- `reset`

These kind strings are justified because they select real Telegram transport methods and help the host choose processing. Do not add a more abstract media ontology.

A generic document uploaded with an image, video, or audio MIME type remains `document`.

### Important animation classification rule

Telegram may include a `document` field alongside a native animation for backward compatibility. Test explicit native animation presence before falling back to generic document classification.

Do not classify a native animation as `document` merely because the compatibility document field exists.

---

## 7. Essential metadata only

Continue using the existing fields:

- `kind`
- `text`
- `mimeType`
- `fileName`
- `durationSeconds`
- `hasMedia`

Do **not** add these proposed fields in this release:

- `width`
- `height`
- `performer`
- `title`
- `emoji`
- `isAnimated`
- `isVideo`

Reasons:

- dimensions are not needed to retrieve or process the bytes;
- performer/title are presentation metadata without a current consumer;
- sticker format is already represented by `kind` plus MIME type;
- sticker emoji can be preserved in existing text when useful;
- every new public field would need schema, migration, projection, edit, archive, documentation, and compatibility maintenance.

If a real host consumer later needs one of these fields, add it as a separate evidence-backed change.

### Text semantics

For private events:

- photo, video, animation, and audio: exact Telegram caption when present;
- sticker: Telegram’s associated emoji as text when present;
- video note: no text unless Telegram later supplies a real textual value;
- no synthetic descriptions.

For group archive rows:

- store the exact caption or sticker emoji;
- use an empty string when no provider text exists because the existing column is non-null;
- do not synthesize `[Photo]`, `[Video]`, or similar prose;
- leave existing voice and document behavior unchanged for compatibility.

The host can combine `kind`, `hasMedia`, and preparation data when constructing model context.

---

## 8. Photo selection

A Telegram photo message supplies several provider-generated renditions, not necessarily the sender’s original upload.

Select one rendition deterministically:

1. maximize checked pixel area `width × height`;
2. use declared file size as a tiebreaker;
3. use stable array order as the final tiebreaker.

Do not describe the retained photo as the sender’s exact original. It is the largest selected Telegram rendition available through the Bot API.

Retain only that rendition in the event or group archive.

---

## 9. MIME and filename behavior

Use Telegram’s MIME type when supplied.

Fallback rules must be honest rather than optimistic:

- photo: `image/jpeg`;
- video: `video/mp4`;
- video note: `video/mp4`;
- static sticker: `image/webp`;
- animated sticker: `application/x-tgsticker`;
- video sticker: `video/webm`;
- animation or audio without a provider MIME type:
  - derive from a recognized safe filename extension when possible;
  - otherwise use `application/octet-stream`.

Do not claim `audio/mpeg` or `video/mp4` merely because those formats are common.

Use a Telegram-supplied filename when available. Otherwise synthesize a safe stable name such as:

- `telegram-photo-123.jpg`
- `telegram-video-note-123.mp4`
- `telegram-sticker-123.webp`

Never expose Telegram’s remote file path as a filename.

Populate existing `durationSeconds` for native types that supply duration.

## 10. Inbound processing

Native media is accepted in:

- authorized private chats;
- allowed invoked group messages;
- allowed passive group archives.

Reuse the existing bounded download path:

- reject a declared size above `max_voice_bytes`;
- enforce the limit again while streaming;
- reject or drop only the affected update;
- do not let one oversized or malformed file freeze later users;
- download only after authorization and group eligibility.

Keep `Config.max_voice_bytes` unchanged for Rust source compatibility. It remains the nonzero limit for all inbound and outbound Telegram media.

Update user-facing unsupported-content feedback compactly, for example:

> Kennedy accepts text, voice notes, native Telegram media, and bounded files here. Use /reset to end this Telegram session.

Do not enumerate every format in ordinary bot feedback.

## 11. Retrieval routes

Do not add another inbound download route.

Expand these existing routes to all retained native media kinds:

- `GET /api/v1/events/{event_id}/media`
- `GET /api/v1/group-messages/{chat_id}/{message_id}/media`

Return:

- exact retained Bot API bytes;
- recorded or honest fallback content type;
- existing `no-store`, `no-cache`, and `nosniff` protections.

Existing voice and document behavior must remain compatible.

Extend the existing private transcription route only to clearly audio-oriented event kinds:

- `voice`
- `audio`
- `video_note`

Do not create a generic semantic-preparation API for private media in this crate. The host can process photos and video bytes directly.

## 12. Outbound native-media API

Keep this route unchanged:

`POST /api/v1/events/{event_id}/file`

It remains the explicit generic `sendDocument` operation.

Add one route:

`POST /api/v1/events/{event_id}/media`

Use `multipart/form-data`.

### Required fields

- `conversationId`: UUID matching the active event binding;
- `kind`: one of the six native kinds;
- `file`: one nonempty bounded binary part.

### Optional fields

- `fileName`
- `caption`
- `complete`

Do not accept the proposed width, height, duration, performer, title, or emoji fields.

### Caption rules

Caption is allowed for:

- photo;
- video;
- animation;
- audio.

Caption is rejected for:

- video note;
- sticker.

Use the same behavior as `/file`:

- whitespace-only caption means absent;
- otherwise preserve it byte-for-byte;
- enforce Telegram’s 1024 UTF-16-unit limit.

### Filename behavior

Use:

1. explicit `fileName`;
2. multipart part filename;
3. a synthesized safe filename appropriate for the native kind.

Validate names using the existing path-free and control-character-free rules.

### Telegram method mapping

- photo → `sendPhoto`
- video → `sendVideo`
- animation → `sendAnimation`
- audio → `sendAudio`
- video note → `sendVideoNote`
- sticker → `sendSticker`

Use `InputFile::memory` with the effective safe filename.

Do not claim that caller MIME metadata is transmitted unchanged if teloxide does not expose that capability. Preserve the validated MIME type in the local archive, but document whether it is caller-declared, inferred, or provider-returned.

Do not fall back to `sendDocument`. Return `telegram_send_failed` so the host can deliberately call `/file` if it wants document semantics.

## 13. Binding, reply, completion, and ambiguity

The native media route must share `/file` semantics:

- event must exist;
- event must remain incomplete;
- `conversationId` must match;
- group delivery replies to the invoking message when possible;
- `allow_sending_without_reply` remains enabled;
- `complete=false` leaves the event active;
- `complete=true` completes only after Telegram accepts the send;
- completion uses the same compare-and-swap binding fence;
- a post-send binding conflict is reported even though Telegram may contain the media.

A Telegram success followed by any local archive or completion failure is an ambiguous external side effect. Surface the failure and do not promise safe blind retries.

For allowed groups, archive the outbound message with:

- exact native kind;
- exact outbound bytes;
- effective filename;
- recorded MIME type;
- exact caption or empty text;
- returned Telegram message ID and date;
- source conversation;
- stable group association;
- invoking-message reply association.

Private outbound media needs no new application-domain archive.

## 17. Required tests

### Existing hardening

- no `IdentitySink` callback executes while the SQLite mutex is held;
- transient retries stop after five total attempts;
- permanent failures make one attempt;
- one principal’s retry/backoff does not block another;
- logs never expose the bot token or Bot API URL;
- passive group-ingress batches preserve existing voice/document metadata.

### Private inbound media

For every new kind:

- accepted after authorization;
- persisted with correct kind;
- listed through `/events`;
- bytes retrieved through the existing media route;
- captions or sticker emoji preserved correctly;
- duration and MIME behavior verified;
- declared and streamed oversize rejected.

### Classification

- native animation with Telegram’s compatibility document field remains `animation`;
- generic documents with image/video/audio MIME remain `document`;
- photo selection maximizes pixel area and uses deterministic tie-breaking;
- static, animated, and video stickers receive correct MIME fallback;
- missing uncertain MIME becomes `application/octet-stream`.

### Groups

For every kind:

- invocation by caption mention where applicable;
- invocation by reply;
- passive allowed-group archive;
- no-caption archive;
- group context includes media metadata;
- background-ingress snapshot includes media metadata;
- preparation may be stored;
- edit replaces bytes and metadata and invalidates old preparation;
- quarantined groups perform zero media downloads and store zero content.

### Outbound media

For every kind:

- correct Telegram method called;
- no document fallback;
- invalid kind rejected;
- duplicate and unknown multipart fields rejected;
- kind-inapplicable caption rejected;
- empty and oversized files rejected;
- filename synthesis and validation;
- group reply behavior;
- exact group archive;
- `complete=false`;
- `complete=true`;
- binding change before send;
- binding change after Telegram success;
- Telegram success followed by archive failure treated as ambiguous.

### Migration and regression

- migrate a seeded actual 0.2.0 schema;
- preserve pending, processing, and complete events;
- preserve private and group events;
- preserve voice and document bytes;
- migration is idempotent;
- fresh install accepts native kinds;
- all existing text, voice, document, reset, edit, group-security, dispatch, cursor, detach, `/file`, origin, and loopback tests remain passing.

### Performance and resource behavior

Use deterministic concurrency tests plus a separate realistic benchmark:

- one large media operation does not prevent another principal from entering processing;
- same-principal FIFO remains intact;
- unrelated principals overlap;
- one saturated principal does not affect siblings;
- panic and retry exhaustion remain local;
- memory use remains bounded by configured limits and dispatch concurrency;
- SQLite lock hold time is measured around large media inserts.

Do not encode fragile sub-200 ms assertions into ordinary shared CI. Record p50/p95/p99 in a dedicated benchmark or acceptance run.
