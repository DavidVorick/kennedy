KENNEDY'S CHATEND AND KWEB OVERHAUL
===================================

Purpose of this document
------------------------

Kennedy, this document explains a major change to the machinery around you.
It is written for you, not merely for a software maintainer. Its purpose is to
give you a correct mental model of:

1. how your sessions and memory used to work;
2. why that design was replaced;
3. how sessions, context, tools, and Kweb writes work now;
4. what behavior is expected from you;
5. what remains deliberately unfinished in this first version.

The short version is:

You used to operate inside a conversation-oriented system with a separate
conversation database, separately prepared history ingress, coarse context
resetting, temporary short node aliases, and application code coordinating
several persistence operations.

You now operate inside a durable box-oriented Chatend. One logical session,
including its source activity and later history ingress, is one append-only
local journal. Everything you can see is a box. You can dehydrate, summarize,
and hydrate individual boxes. All permanent knowledge effects from one session
are staged locally and committed together in exactly one transactional Kweb
write. Completed Session History is stored in Kweb rather than duplicated in a
conversation database.


PART I: HOW THE OLD SYSTEM WORKED
=================================

The previous system's mental model
----------------------------------

The old system was primarily organized around conversations and transcript
history. A conversation had a transcript-like active context, application
metadata in Conversation History, and a later memory-ingress process that
turned completed conversation material into Kweb updates.

This gave you several overlapping ideas to reason about:

- the live conversation;
- the conversation record stored by Conversation History;
- a conversation archive or provenance object;
- memory-ingress work derived from that conversation;
- Kweb node updates performed through application APIs;
- provider-side context or thread state;
- application-generated short aliases for Kweb nodes.

These were related, but they were not one durable unit. The server had to
coordinate them.

Conversation History
--------------------

Conversation History was backed by a large SQLite database. It stored active
and completed conversations, transcripts, metadata, processing state, and
other application information. Completed conversation history therefore
existed outside the Kweb object store as a second permanent history system.

The frontend treated Conversation History as a rich local database. It could
list local records and had concepts such as purging them. The application had
to keep that database, Kweb persistence, and memory-ingress state consistent.

History ingress
---------------

Completed conversational material was submitted into a shared Memory Ingress
queue. Conversation history and audio work were both represented as jobs in
that queue. History ingress operated on a prepared conversation archive rather
than continuing directly from the exact durable state of the original live
session.

This made the source conversation and the history-ingress work feel like
separate jobs, even though they were logically two phases of the same session.
It also created more application state to checkpoint, retry, reconcile, and
recover.

Context management
------------------

The old system used coarser context concepts. "ResetContext" could discard and
rebuild a large portion of active context. Earlier design language also used
"blanched" for removed content and "dirty" for an out-of-date compact
representation.

Those ideas did not preserve enough visible continuity. They made it harder
for you to reason about where a piece of information originally appeared,
where it moved, whether it was still current, and how to restore exactly the
part you needed.

Kweb identity and navigation
----------------------------

The old backend was based on kweb-db-core. The frontend did not normally give
you the actual durable Kweb identifiers. It handed you shorter temporary
aliases. Those aliases made individual calls convenient, but they were not
stable names you could carry across sessions.

The old adapter also exposed connection behavior through older terms such as
active and fanout connections. The new database's stored connection classes
are simply fixed connections and recent connections. Higher-level operations
such as consolidation still exist as Kennedy tool behavior, but they are no
longer separate database connection types.

Kweb persistence
----------------

The older application path coordinated provenance archives, objects, node
changes, idempotency receipts, and application metadata as several related
operations. Even when each individual piece was durable, there could be a
window in which one database had committed and another had not.

Objects were commonly embedded or passed around in JSON-oriented application
structures, including Base64 data URLs. This increased storage and memory cost
and mixed permanent object custody with conversation serialization.

The central problem
-------------------

The old design was not wrong because conversations, archives, queues, or
SQLite are inherently bad. It was wrong for the desired invariant:

    One complete Kennedy session should be one recoverable working unit and
    should produce one permanent Kweb transaction.

The old system spread that unit across too many stores and abstractions.


PART II: THE NEW SYSTEM AT A GLANCE
==================================

The new durable unit is a session
---------------------------------

A session now means the complete lifecycle of one activity:

- its starting system prompts;
- automatic user-root and Kennedy-root loads;
- user messages or source material;
- your replies;
- tool calls and tool results;
- object attachments;
- context transformations;
- the history-ingress continuation, when the session type has one;
- all staged Kweb changes;
- the final immutable archive.

A normal browser or Telegram conversation has two phases:

1. Source phase: you talk with the user and read the Kweb.
2. History-ingress phase: after the source ends, you review the same session
   and stage any permanent Kweb changes.

These phases are not two sessions. They use the same session ID and the same
append-only journal. Exactly one history-ingress run handles exactly one
source session.

Self time and audio ingress use the same durable concepts, although their
lifecycle details differ and are explained later.

The new permanent unit is one Kweb transaction
-----------------------------------------------

When a writable session finishes, the server constructs one real
kcode-kweb-db transaction containing:

- all user-supplied objects accepted during the session;
- the complete immutable session archive object;
- every node created by the session;
- every complete node update;
- every fixed-connection change;
- every recent-connection change.

That transaction commits atomically inside Kweb. There is no separate
permanent conversation archive transaction and no series of individually
committed node edits.

Before the final commit, a successful write tool means "staged locally." It
does not mean "already visible globally."


PART III: THE CHATEND JOURNAL
============================

One append-only file per active session
---------------------------------------

Every in-progress session has one file:

    data/sessions/in-progress/<session UUID>.chatend

The file is an append-only journal. The server does not continually rewrite a
large JSON snapshot. Instead, each accepted transition is appended in order.

The journal contains:

- session metadata and lifecycle transitions;
- every event and box;
- the canonical contents and visible representation of boxes;
- browser command state;
- provider requests and usage receipts;
- tool calls and tool results;
- the staged Kweb transaction plan;
- raw attached-object records;
- history-ingress progress;
- finalization state.

JSON is used for evolving Chatend control records because the session format
will likely gain fields frequently. Raw object bytes are stored as raw bytes,
not expanded into Base64 JSON.

Frames have a stable binary envelope containing a frame type, a canonical
little-endian length, and a SHA-256 checksum. Replay accepts frames until it
finds an incomplete or checksum-invalid frame, then truncates that frame and
everything after it. Checksum-valid structural or semantic failures are
programming or compatibility errors.

Durability rule
---------------

An accepted update is appended as one checksummed frame. A naturally batched
operation is one frame containing all of its ordered events. The server uses
ordinary append I/O without an explicit flush or fsync. Data already accepted
by the kernel remains available after ordinary process termination; sudden
power loss may remove a suffix, which replay detects and discards.

The journal remains authoritative until the session's Kweb transaction has
committed and local completion has been recorded.

A successful tool result is therefore staged in the local session log rather
than existing only in model context, but it does not carry a separate
power-loss durability guarantee.


PART IV: EVERYTHING YOU SEE IS A BOX
====================================

The box model
-------------

Every durable provider-visible context component is now a box. There is no
model-visible message, system instruction, Kweb node, history inspection, or
controller notice outside this model. Native tool responses are transient
inputs to the already-running provider turn; ordinary tool responses are also
captured as result boxes, while LoadNode uses the Kweb boxes it updates.

Examples include:

- system prompts;
- one box for each user message;
- one box for each Kennedy message;
- loaded Kweb nodes;
- each individual tool call;
- each ordinary tool result;
- controller notices;
- hydrated history events;
- document and audio material presented to you.

If you make several tool calls in one response, every call and completion is
recorded independently in chronological order. A manual LoadNode completion
is a compact non-projected journal receipt rather than a duplicate result
box.

Stable box identity
-------------------

A box ID is the event ID that created the box. The box keeps that ID for its
whole lifetime.

The box may later acquire:

- a newer canonical revision;
- a different visible representation;
- a later occurrence in the chronology;
- a stale marker;
- additional object references;
- a retired state.

None of those changes creates a new identity for the box.

Canonical content versus visible representation
------------------------------------------------

The canonical content is the latest actual value owned by the box's source.
The representation is what is currently included in your active provider
context.

Keeping those concepts separate is essential:

- Dehydrating a box does not destroy its canonical content.
- Summarizing a box does not replace its canonical content.
- Dehydrating a Kweb node does not unload the node from tool state.
- A tool updating a box does not silently rewrite your summary.

Hydrated
--------

A hydrated box exposes its latest canonical contents in active context.

Use:

    DehydrateBox {"boxId":47}

to compact it when you no longer need the contents immediately.

Dehydrated
----------

A dehydrated box omits substantive contents while retaining compact identity,
lineage, revision, restoration information, and chronological markers.

Use:

    HydrateBox {"boxId":47}

to restore the latest canonical contents.

Summarized
----------

A summarized box displays replacement text authored by you:

    SummarizeBox {
      "boxId":47,
      "summary":"The exact compact text I want to retain."
    }

Your summary is a context-management aid. It is not a mutation of the source
message, Kweb node, tool state, or archived canonical content.

Stale
-----

A summarized or dehydrated representation becomes stale if the canonical
source advances beyond the revision on which that representation was based.

Stale does not mean corrupt. It means:

    The compact representation is older than the latest canonical value.

The controller does not spend context explaining the difference. If the
difference matters, hydrate the box and inspect the latest value.

The former word "dirty" is retired. Use "stale."

Continuation markers
--------------------

When the current occurrence of a stable box moves later in the chronology, a
compact continuation marker remains where it used to appear. The marker points
to the later occurrence.

These markers let you understand how active context evolved without repeating
the full contents at every old location.

The former word "blanched" is retired. Use "dehydrated."

Who controls boxes
------------------

You control ordinary box hydration, dehydration, and summarization. The user
and frontend may inspect box state but cannot change it.

The controller performs one deliberate context-fitting transformation when a
terminated source session is prepared for history ingress. It always preserves
your current summaries, tentatively hydrates the other boxes, and only reduces
eligible boxes when the resulting context would exceed 75 percent of the
ingress model's context window. Conversation messages, the system prompt, full
direct/fixed/active Kweb nodes, and short tool invocations are protected.


PART V: PROVIDER REQUESTS AND TOOLS
==================================

No hidden provider conversation
-------------------------------

Every inference is built from the current Chatend projection. The server does
not depend on a hidden provider-side thread as an additional source of truth.

Provider input and provider usage measurements are recorded in the journal.
When the provider returns an exact input-token measurement, that measurement
recalibrates the exact inference manifest that produced it. Later estimates
continue from the measured baseline.

call_ktool remains registered
-----------------------------

The provider-level function call_ktool remains registered for every inference.
Tool definitions and operating instructions are in system-prompt boxes.

This distinction matters:

- Dehydrating the system-prompt box that explains a tool does not unregister
  call_ktool.
- It may, however, cause you to forget a tool's contract.
- You are responsible for keeping or restoring the instructions you need.

A native call looks like:

    {
      "name":"LoadNode",
      "arguments":{"identifier":"AAECAwQF"}
    }

Multiple calls may be issued before the next inference. A failed tool result
means that call did not succeed.

The JSON invocation is intentional. Ktool results, however, are raw text:
there is no result JSON envelope, Serde rendering, or pretty-printing. An
ordinary result is retained as one box containing the same raw text. Managed
Rust library tools follow this ordinary path, so opening a library returns one
box containing its complete textual snapshot.

A successful LoadNode response is different from ordinary tool results: it
contains the exact Kweb boxes created or revised by the call, rendered exactly
as Chatend renders their current hydrated, summarized, or dehydrated
representation. It contains no duplicate node data and creates no generic
"Kennedy tool result" box. A failed load and an unchanged repeat load return
short plain text.

There is no ResetContext
------------------------

ResetContext no longer exists. Use the smallest relevant operation:

- DehydrateBox to remove contents temporarily.
- SummarizeBox to keep your own compact replacement.
- HydrateBox to restore current canonical contents.
- During history ingress, HydrateEvent to inspect a persisted event.
- During history ingress, DehydrateEvent to retire that inspection box.


PART VI: CONTEXT BUDGETS
========================

Source sessions: 70 percent
---------------------------

A source session that will later go through history ingress may use at most
floor(70 percent) of the selected model's effective context window.

The remaining capacity is not wasted. It is reserved for the later
history-ingress phase, which may need to hydrate source events, inspect Kweb
state, reason about permanent memory, and call tools.

History ingress: 75 percent
---------------------------

History ingress may use floor(75 percent) of the effective context window of
the model being called. The ceiling therefore changes with the selected
model; it is not a fixed byte or token constant.

Capacity errors
---------------

If hydrating a box, hydrating an event, or accepting a tool result would exceed
the applicable limit, the operation is rejected and you receive an error.

The appropriate response is normally to dehydrate or summarize other boxes,
then retry only if the rejected material is still useful.

The 72 percent emergency boundary
---------------------------------

If repeated failures leave a source session so full that even another useful
capacity error cannot be added without crossing 72 percent, the controller
force-ends the source phase and sends the same journal to history ingress.

This is an emergency escape hatch, not an ordinary rollover target. Manage
boxes before reaching it.

If history ingress cannot progress at 75 percent
------------------------------------------------

If history ingress reaches its limit and no further useful work fits, the
server completes with the useful staged work accumulated so far. There is no
requirement to force one more model turn.


PART VII: KWEB IDENTITY AND NAVIGATION
=====================================

Canonical identifiers
---------------------

Committed Kweb node and object IDs are real eight-character URL-safe Base64
identifiers. Node IDs and object IDs occupy disjoint domains so they cannot
collide.

You now see canonical node IDs directly. There are no frontend-generated fake
short aliases. The same canonical ID names the same durable resource across
sessions.

Prefer names when writing prose to yourself, but use the exact identifier in a
tool call.

Pending identifiers
-------------------

New session-local nodes and objects use:

    pending:<number>

For example:

    pending:47

Boxes, pending nodes, and pending objects share one monotonically increasing
numeric identity space. If event 47 allocates a pending object, there cannot
also be a box 47 or pending node 47.

Pending IDs are:

- stable for the rest of the session;
- persisted across restart;
- never reused;
- usable by later staged operations in the same session;
- resolved to canonical IDs during final Kweb transaction construction.

The immutable session archive may retain pending IDs in its own internal
chronology. The successful commit result separately returns the permanent
mapping needed by live application state.

Roots
-----

Your root node and the user's root node are application-owned identity
mappings stored by canonical ID. They are not special responsibilities of the
Kweb database.

Both roots are loaded automatically at session startup through ordinary
LoadNode behavior. All full directly loaded, fixed, and active node boxes are
protected from automatic history-ingress dehydration.

Loading nodes
-------------

LoadNode accepts a canonical ID:

    LoadNode {"identifier":"AAECAwQF"}

It loads or refreshes the node and its current recent-connection closure.
There is no fixed "three nodes" or other direct-node count limit. The active
Chatend context budget is the practical limit.

Repeating LoadNode refreshes the existing Kweb-owned boxes. It does not create
duplicate node boxes. If the box is summarized or dehydrated and the node has
changed, the representation remains compact and becomes stale.

A manual load occurs while a provider turn is already running. Updating the
journal cannot retroactively change that turn's input, so the native tool
response returns the new or revised Kweb boxes in their persistent layout
order. This is a delta, not a second storage format: each returned block is
the exact text of the corresponding current Chatend projection item. The
journal records only the identifier, changed box IDs and count, duration, and
success or failure. That compact structured completion event is not projected
unless Kennedy later explicitly inspects it with HydrateEvent during history
ingress.

The loaded-node display is globally ordered and deduplicated:

1. Every directly loaded node has one full box.
2. Every unique fixed connection of those nodes has one full box.
3. Every unique active connection (the first eight recent connections) has one
   full box.
4. Each directly loaded node has one fanout box containing the ID and summary
   of each fanout node not represented earlier.
5. One box contains the previously unseen fixed and active neighbors of all
   fixed nodes, using ID, name, and summary.
6. One box does the same for all active nodes.
7. One final box contains the ID and name of every still-unseen fanout
   connection of the fixed and active nodes.

A full node box contains exactly its ID, name, summary, long description, and
identifier-only fixed, active, and fanout lists. If a node qualifies for
several roles, the earliest role above wins and its descriptive text is not
emitted again.

Connections
-----------

The database stores two distinct ordered connection arrays:

- fixed_connections;
- recent_connections.

The database does not impose an application-level count limit on either.

Fixed connections are arbitrary numbered placements under your control. They
do not inherently mean priority, task status, importance, or completion.

Recent connections are the stored dynamic graph relationships. Operations such
as ConnectNodes and ConsolidateFanout are higher-level Kennedy behaviors that
rewrite those arrays; "fanout" is not a third database connection type.


PART VIII: READS, WRITES, AND THE GLOBAL WRITE LANE
==================================================

Read-only source work
---------------------

Ordinary browser and Telegram source sessions are Kweb-read-only. They may
load and inspect nodes in parallel with other read-only sessions.

You should freely use LoadNode and other read tools when they improve your
answer. Do not expect write tools during the conversational source phase.

History ingress acquires write access
-------------------------------------

When the source ends, its history-ingress phase eventually acquires the one
global Kweb write lane. Only one Kweb-writing session runs at a time in V1.

The lane also serializes:

- self time;
- audio ingress;
- other backend-owned Kweb-writing sessions.

Read-only sessions do not wait for this lane.

Revalidation
------------

A conversation may have loaded nodes before waiting for write access. Another
session may change those nodes while this session waits.

After acquiring the writer lane, the controller revalidates loaded nodes. If a
node changed:

- its box receives a newer canonical revision;
- a summarized or dehydrated representation becomes stale;
- a compact system update occurrence identifies the affected box;
- the controller does not generate a diff or explanation;
- you hydrate the node if the new value matters.

Self time is different: it obtains the writer lane before initially loading
Kweb state, so it does not begin from a view that became stale while waiting.

Read-your-writes
----------------

Write tools mutate a durable local KwebPlan. They also update the session's
Kweb boxes immediately, so later calls in the same session see the staged
result.

This is read-your-writes behavior. It is not a global commit.


PART IX: STAGING KWEB CHANGES
=============================

Write tool success means staged
-------------------------------

These tools stage effects:

- ConnectNodes;
- ConsolidateFanout;
- SetFixedConnection;
- CreateNode;
- UpdateNode;
- object attachment through the applicable session flow.

All staged changes remain recoverable in the Chatend journal until final
commit.

CreateNode
----------

CreateNode returns a pending ID:

    CreateNode {
      "parentIdentifiers":["AAECAwQF"],
      "ownerIdentifier":"AAECAwQH",
      "shortName":"New Memory",
      "shortDescription":"A compact description.",
      "longDescription":"The complete durable knowledge."
    }

The returned pending ID may be used in later calls during the same session.
Parents and owners must already be fully available.

UpdateNode
----------

UpdateNode supplies complete replacements for the node's descriptive fields
and owner:

    UpdateNode {
      "identifier":"AAECAwQF",
      "ownerIdentifier":"AAECAwQH",
      "newShortName":"Updated Memory",
      "newShortDescription":"Updated description.",
      "newLongDescription":"Complete updated durable knowledge."
    }

Omitted old text is not implicitly retained. Build the complete intended
replacement.

At the database layer, node updates also replace the complete fixed and recent
connection arrays in the same transaction. Higher-level Kennedy tools maintain
those complete arrays in the staged plan.

SetFixedConnection
------------------

SetFixedConnection changes one directional numbered fixed slot:

    SetFixedConnection {
      "parentIdentifier":"AAECAwQF",
      "childIdentifier":"AAECAwQG",
      "slot":1
    }

Slots are positive and contiguous. Use "blank" as childIdentifier to clear a
slot.

ConnectNodes
------------

ConnectNodes stages every supplied node as a recent connection of every other
supplied node. It requires at least two distinct, fully available nodes.

ConsolidateFanout
-----------------

ConsolidateFanout is still available as a graph-maintenance operation. It
removes named recent connections from a parent, retains an aggregator under
the parent, and places those named connections under the aggregator.

Again, this does not imply that Kweb stores a special fanout-connection class.


PART X: OBJECTS
===============

Object custody
--------------

When the user supplies a file, image, voice note, or other supported object,
the communication adapter first puts the original bytes into the Chatend
journal. The visible user box refers to it using a pending object ID.

The bytes themselves are not inserted into your provider context. You see a
cheap reference such as:

    Object provided: pending:47

This reference can be retained and attached to more than one node without
copying the object into model text.

Browser uploads use multipart raw data. They are not Base64-encoded into JSON.

Object limits
-------------

V1 permits:

- up to 32 GiB for one object;
- up to 32 GiB aggregate staged object payload in one transaction.

The target machines have enough memory for this V1 limit. There is no smaller
application policy imposed merely as a precaution.

Two disk writes in V1
---------------------

An accepted incoming object is first written to the Chatend journal so the
session can survive a restart.

At final commit, the server reads it and supplies it through the current
kcode-kweb-db transaction API. Kweb writes it into the permanent object store.

The extra disk I/O is deliberate. A more complex staged-file adoption or
zero-copy API was rejected for V1 and may be added later.

Permanent retention
-------------------

After commit, accepted session archives and objects are immutable Kweb data.
Removing a record from a UI would not mean deleting that accepted permanent
history. The new frontend therefore does not offer a misleading purge action.


PART XI: HISTORY INGRESS
========================

What history ingress starts with
--------------------------------

History ingress continues the same session journal after the source phase has
terminated.

The controller:

1. records source termination;
2. installs the history-ingress system prompt and the current model's context
   window;
3. acquires the global write lane;
4. revalidates previously loaded Kweb nodes;
5. retains every current Kennedy-authored summary;
6. tentatively hydrates everything else;
7. if the result would exceed 75 percent, reduces eligible boxes from largest
   to smallest until it fits;
8. exposes the source-history skeleton.

The full source history has not been deleted. Dehydrated and programmatically
summarized boxes retain canonical content and can be hydrated later.

Inspecting source history
-------------------------

Use the skeleton to decide what matters, then inspect individual persisted
events:

    HydrateEvent {"eventId":104}

This creates an ingress inspection box containing that exact event.

When it is no longer useful:

    DehydrateEvent {"eventId":104}

This retires the inspection box. It does not mutate the original source event
or history.

Your job during ingress
-----------------------

Review enough source material to identify durable knowledge worth preserving.
Load the relevant current Kweb nodes. Stage creates, updates, objects, and
connections. Use summaries and dehydration to control context.

A normal text answer does not finish history ingress. Continue until every
useful update you can make has been staged successfully, then call:

    EndSession {}

EndSession constructs and finalizes the one Kweb transaction containing the
archive, objects, and all staged graph effects.

Do not merely say that ingress is complete. Call EndSession.


PART XII: SESSION HISTORY
=========================

Session History replaces Conversation History
----------------------------------------------

The application domain is now called Session History. The Rust package keeps
the historical internal package name kennedy-conversation-history, and the
compatibility HTTP routes still use /api/v1/conversations, but those names do
not describe the new storage model.

In-progress records
-------------------

An in-progress session's lifecycle, contents, commands, retries, and ordering
are all in its .chatend journal. There is no second SQLite conversation record
that must mirror it.

Completed records
-----------------

After a successful Kweb commit, the server appends only the canonical archive
object ID to:

    data/session-history.txt

The archive does not store its own permanent object ID, so there is no circular
encoding problem.

When the frontend needs completed details, it loads that immutable archive
object from Kweb. There is no local duplicate archive and no rich completed
metadata database.

There is no purge API for completed Session History.

Legacy history
--------------

The old conversation database is no longer runtime persistence. Completed old
history and six unfinished legacy sessions were moved under data/archive for
offline retention and manual ingress if desired.

There is no compatibility loader. Do not expect old open conversations to
reappear as synthetic boxes, and do not invent continuity with them unless the
user manually provides their archived text.


PART XIII: SESSION-TYPE WORKFLOWS
================================

Browser and Telegram conversations
----------------------------------

During the source phase:

- help the user normally;
- inspect Kweb as useful;
- manage boxes before approaching the 70 percent limit;
- remember that Kweb is read-only;
- respond normally to end a turn.

When the source session ends:

- the same journal enters history ingress;
- it waits for the writer lane;
- you inspect selected prior events;
- you stage permanent Kweb effects;
- you call EndSession;
- one transaction permanently records the result.

Self time
---------

Self time acquires the writer lane before it loads Kweb. All relevant tools
are available in the session.

A normal answer does not end self time. The controller reports remaining time
and lets you continue doing concrete work.

Self time does not have a later history-ingress phase. If something should be
saved to Kweb, stage it during self time before ending.

When ready, call EndSession. If enough scheduled time remains, EndSession may
include one non-empty message for the next clean-slate self-time session:

    EndSession {
      "message":"Continue by reviewing the nodes under the research root."
    }

This handoff is not ResetContext and is not a general session-segmentation
framework. It is one explicit message to a new self-time session.

Audio ingress
-------------

AudioIngress still uses its durable specialized queue for ordered transcript
pieces. Conversational history no longer enters that queue.

In an audio-ingress session:

- review the supplied transcript piece;
- load the Kweb nodes needed to place its durable knowledge;
- stage all useful graph changes;
- call EndSession after every required mutation succeeds.

A normal answer does not finish audio ingress.


PART XIV: CRASHES, RETRIES, AND EXACTLY-ONCE LIMITS
==================================================

What is recoverable
-------------------

Before final Kweb commit, the Chatend journal's appended valid prefix contains:

- accepted messages and objects;
- box state;
- provider work;
- tool activity;
- the semantic KwebPlan;
- history-ingress progress.

A restart replays this file. Pending IDs remain stable, and staged objects do
not need to be uploaded again merely because the process restarted.

Kweb transaction duplicate behavior
------------------------------------

kcode-kweb-db itself recognizes an identical transaction it has already
processed. Resubmitting the same signed transaction is a successful no-op.
The database also enforces transaction dependency ordering for gossip-origin
transactions.

The accepted V1 crash window
----------------------------

KennedyServer does not yet have an API for preparing the exact signed
TransactionPackage before submission. It appends the Chatend journal and
semantic plan, then constructs and finalizes the Kweb transaction without
explicitly fsyncing the journal.

There is therefore a narrow window:

1. Kweb may successfully commit.
2. KennedyServer may crash before recording local completion and the returned
   canonical IDs.

On restart, the semantic plan can be reconstructed, but constructing it again
does not guarantee byte-identical transaction bytes or the same randomly
allocated resource IDs. The library's duplicate no-op protection therefore
cannot fully close this application-level window.

This risk was explicitly accepted for V1. Do not describe the complete
KennedyServer finalization path as perfect exactly-once recovery.

Future work may add a prepared TransactionPackage API and remove this window.


PART XV: WHAT HAS NOT CHANGED
=============================

Despite the extensive backend rewrite, your basic role is unchanged:

- help the user;
- use the Kweb as durable long-term memory;
- navigate from your root and the user's root;
- decide what knowledge is worth retaining;
- use tools deliberately;
- keep durable nodes clear, accurate, and connected;
- respect the difference between immediate conversation and permanent memory;
- use self time for autonomous useful work;
- use history ingress to integrate session knowledge.

The familiar higher-level Kweb operations remain:

- loading nodes;
- creating nodes;
- updating nodes;
- connecting nodes;
- managing fixed connections;
- consolidating high fanout.

The important change is when and how writes become permanent. They are staged
inside one recoverable session and then committed atomically as one Kweb
transaction.


PART XVI: PRACTICAL RULES FOR KENNEDY
====================================

1. Think in boxes, not in one undifferentiated transcript.

2. Treat a box's canonical content and active representation as separate.

3. Use "dehydrated," "summarized," and "stale." Do not use the retired terms
   "blanched" or "dirty" for these states.

4. Do not look for ResetContext. Manage individual boxes.

5. Keep system/tool instruction boxes available when you still need their
   contracts. call_ktool remains registered even if you hide the explanation.

6. Use canonical eight-character Kweb IDs exactly as shown. Do not expect fake
   per-session short node aliases.

7. Treat pending:N as a durable session-local resource ID. It is valid only
   within the session until final commit resolves it.

8. Remember that a successful Kweb write tool is staged, not globally
   committed.

9. Expect read-your-writes inside the session.

10. During history ingress, inspect source events selectively with
    HydrateEvent instead of hydrating the whole source chronology.

11. If a compact Kweb box is stale, hydrate it only if the latest canonical
    value matters. Do not expect an automatic diff.

12. Manage source context below 70 percent. Do not use 72 percent as a target.

13. During history ingress or audio ingress, do not merely announce completion.
    Call EndSession after useful staged work is complete.

14. During self time, make Kweb changes before EndSession because there is no
    later history ingress.

15. Do not assume a deleted or hidden UI row would erase permanent history.
    Completed archives and accepted objects are immutable Kweb data.

16. Do not expect legacy open conversations to load. They were archived
    offline without synthetic conversion.


PART XVII: EXAMPLE END-TO-END CONVERSATION
==========================================

Suppose the user tells you:

    "I have moved the greenhouse monitoring service to a new machine. Here is
    the deployment diagram."

Source phase:

1. The user message is appended and exposed as one user-owned box.
2. The diagram's raw bytes are appended to the journal as an object record,
   perhaps pending:47.
3. The user box refers to "Object provided: pending:47."
4. You load relevant Kweb nodes by their real canonical IDs.
5. Each loaded node and each tool call/result is represented by a box.
6. You answer the user. You may summarize or dehydrate boxes to stay below the
   source budget.

History-ingress phase:

1. The same session journal enters ingress; no second conversation is created.
2. Your source summaries remain summarized.
3. Other boxes remain hydrated unless largest-first fitting was required.
4. The ingress prompt, conversation messages, and full direct/fixed/active
   Kweb nodes are protected from automatic dehydration.
5. You inspect any dehydrated material that is relevant.
6. You reload or inspect the deployment nodes.
7. You stage UpdateNode or CreateNode calls.
8. You attach pending:47 where appropriate.
9. Every successful mutation updates the local read-your-writes view.
10. You call EndSession.

Final commit:

One Kweb transaction creates the diagram object, creates the immutable session
archive object, applies every node creation and update, and stores the final
connection arrays. The commit returns canonical IDs for pending resources.
The archive object's canonical ID is appended to session-history.txt, and the
in-progress journal can then be removed.


PART XVIII: DELIBERATE V1 BOUNDARIES
===================================

The current system intentionally leaves several optimizations for later:

- Gossip protocol integration is not implemented yet.
- The Kweb writer lane is global rather than fine-grained.
- Object commit performs a second disk write rather than adopting the staged
  file directly.
- The exact signed TransactionPackage is not persisted before commit, leaving
  the narrow finalization crash window described above.
- The current random-ID transaction builder cannot create a cycle of mutually
  dependent new nodes in one session without a future ID-reservation API.
- Provider caching favors a simple, correct full projection rather than an
  elaborate continuation protocol.
- Objects larger than 32 GiB require a future streaming protocol.

These are known boundaries, not hidden guarantees. Work normally within them
and do not invent APIs or recovery properties that are not present.


FINAL MENTAL MODEL
==================

When you need one compact way to remember the overhaul, use this:

    A Kennedy session is one append-only, restart-safe Chatend journal.
    Everything I can see is a box with stable identity.
    I manage context by hydrating, dehydrating, and summarizing boxes.
    Canonical Kweb IDs are real and stable; pending IDs are session-local.
    Kweb writes are staged with read-your-writes behavior.
    History ingress continues the same session and selectively inspects it.
    EndSession commits the archive, objects, and all graph changes together in
    one Kweb transaction.
    Completed local history is only a list of immutable Kweb archive object
    IDs.

That is the new architecture you are operating inside.
