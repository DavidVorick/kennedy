Kennedy context-management rendering choices
=============================================

Purpose
-------

This document explains why Kweb context is rendered the way it is. It is meant
to preserve the model-facing contract and the ownership boundaries behind it,
not merely describe where the current functions happen to live.

The important goals are:

* give the model complete, readable node data without repeating it;
* make the number and purpose of Kweb boxes predictable;
* keep recent connections useful for navigation without silently loading them;
* preserve visible tool-call/result continuity when stateful boxes change; and
* keep Kweb policy, Chatend history behavior, and KennedyServer integration
  owned by the appropriate components.


Ownership boundaries
--------------------

kcode-kweb-context owns Kweb context policy and provider-facing Kweb content:

* typed node and connection data;
* the ordered sets of explicitly loaded and fixed nodes;
* loaded-versus-fixed precedence and global deduplication;
* staged projections;
* Kweb box kinds and names;
* the common full-node body formatter; and
* the one-box recent-connection projection.

kcode-session-history owns generic Chatend behavior:

* stable box identity and occurrence history;
* hydrated, dehydrated, summarized, and stale representations;
* generic box headers;
* the opt-in concise header form; and
* the generic "[box updated]" continuity marker.

KennedyServer remains integration glue:

* fetch the requested Kweb node and all of its fixed connections;
* convert a staged Kennedy plan into the library's typed draft data;
* convert BoxSpec values into Chatend BoxContent;
* reconcile logical Kweb slots with stable Chatend box IDs; and
* reconstruct loaded-node intent from durable LoadNode tool history.

The context library intentionally does not fetch over HTTP, persist Chatend
events, or know about KennedyServer sessions. Chatend intentionally does not
know what a Kweb node is. This keeps both library APIs small and prevents two
components from independently interpreting the same policy.


Box cardinality and order
-------------------------

The projection has these boxes, in this order:

1. One full box for every explicitly loaded node.
2. One full box for every distinct fixed connection of those loaded nodes,
   unless that node is already explicitly loaded.
3. One full staged box for every newly created pending node.
4. Exactly one global recent-connections box, including when it says "None."

An explicitly loaded node takes precedence over the fixed role. A node must not
appear once as loaded and again as fixed.

Fixed loading is one level from explicitly loaded nodes. A fixed node is
available in full, but its own fixed connections do not recursively become full
nodes merely because it was fixed. A later explicit LoadNode call promotes a
fixed node to the loaded role without creating a duplicate box.

Staged updates to existing nodes retain the node's loaded or fixed box kind.
They change that full box's projected body. Only a newly created pending node
uses the staged box kind.

The recent box is global across loaded, fixed, and staged projected nodes.
Every recent reference appears at most once, deduplicated by canonical or
pending node ID. A recent reference still belongs in the recent box if its
target also has a full loaded or fixed box: the full box describes the node,
while the recent entry records the projected graph relationship.

Recent-entry order follows the first occurrence while visiting projected full
nodes in layout order, then staged creates. Do not replace this with sorting
unless the model-facing ordering policy is intentionally changed.


There is no active-connection category
--------------------------------------

"Active connection" used to mean that a bounded prefix of recent connections
was promoted into full context. That category no longer exists.

All recent connections are fanout-only navigation summaries. They are not
automatically promoted to full nodes, there is no active-connection count
limit, and full node bodies contain no active-connection field.

A recent node becomes full only through an actual full-node rule:

* the model explicitly loads it; or
* it is a fixed connection of an explicitly loaded node.

Do not reintroduce active-node arrays, active/fanout splitting, per-role recent
aggregates, or a prefix limit under a different name.


Full-node headers
-----------------

Kweb full-node boxes use Chatend's concise header. For a hydrated loaded node,
the exact header is:

[box {box_id} | Kweb loaded node | hydrated]

The other full box names are:

* Kweb fixed connection
* Kweb staged node

Their hydrated headers therefore have the same structure:

[box {box_id} | Kweb fixed connection | hydrated]
[box {box_id} | Kweb staged node | hydrated]

The node ID and short name are deliberately absent from the header because they
already appear in the body. Repeating them made a high-frequency part of the
context longer without adding information.

The Chatend owner is also absent from these headers. A Chatend owner such as
"tool:kweb:..." describes internal box control, not Kweb resource ownership.
Showing it next to node data made two unrelated meanings of "owner" easy to
confuse.

Concise headers are opt-in Chatend behavior, not the default for every box.
Other Chatend objects may still need their internal owner label. Do not remove
owners from all generic headers merely to preserve the Kweb format.

Chatend may substitute "dehydrated" or "summarized" for "hydrated" and may add
"stale" when those representation states genuinely apply. The concise choice
only removes the internal owner segment; it does not bypass Chatend lifecycle
state.


Full-node bodies
----------------

Loaded, fixed, and staged boxes use one formatter. Their body fields and order
are:

Node ID: {identifier}
Node name: {short_name}
Node summary: {short_description}
Node owner ID: {owner}
Node long description:
  {long_description}
Fixed connection IDs: {comma-separated IDs or "none"}
Recent connection IDs: {comma-separated IDs or "none"}

Empty text values render as "(none)". Empty connection lists render as "none".
Every long-description line is indented by two spaces.

Kweb resource ownership belongs in "Node owner ID" in this body. It must not be
replaced by the Chatend box owner.

The bodies are intentionally the same across loaded, fixed, and staged node
boxes. Their box kind communicates why they are present. Different field sets
would make a node's visible capabilities depend on how it entered context and
would complicate both the model's interpretation and regression testing.

Object IDs remain typed node state and staged-plan data, but they are not
rendered in this full-node context body. Adding another high-frequency field
requires an explicit model-context decision; it should not happen merely
because the data is available in metadata.


The global recent-connections box
---------------------------------

The box name is:

Kweb recent connections

Its body begins:

Recent connections

Each entry has the exact compact shape:

{node_id} · {short_name}: {short_description}

When there are no recent connections, the body is:

Recent connections
None.

The name and short description are required for every entry. The projection
must fail clearly if it cannot resolve them rather than silently emitting an
ID-only or "unknown" entry. Resolution prefers staged target data, then the full
stored target node, then the connection summary supplied by Kweb.

Earlier designs used separate fanout boxes per loaded node and separate
aggregates for fixed and active nodes. That produced too many boxes, repeated
the same connection in different categories, and made global deduplication
harder to reason about. One global box gives recent connections one clear
purpose and one stable location.


Stable box identity and updates
-------------------------------

Kweb logical slots are stable:

* a canonical node ID for loaded and fixed full boxes;
* a pending node ID for staged-create boxes; and
* "recent-connections" for the global recent box.

KennedyServer reconciles those slots with existing Chatend tool slots so an
updated node retains its box ID. It does not create a new independently owned
box for every revision.

When a later occurrence supersedes an earlier occurrence of any Chatend box,
the earlier projected position contains exactly:

[box updated]

This marker is generic Chatend behavior. Its purpose is history continuity: a
tool call followed by a stateful box should not later look as though the tool
returned nothing. The marker says that the result existed, succeeded, and was
moved forward because its state changed.

The marker deliberately contains no box-specific explanation. The current box
occurrence contains the identity, name, representation, and content. Repeating
those details in every old position adds noise.

Do not create Kweb-specific "Kweb update for box ..." notice boxes. Those
notices duplicate the generic occurrence history, consume context, and assign
a generic history responsibility to the Kweb integration.


LoadNode results
----------------

LoadNode updates the shared Kweb boxes and returns the exact changed current
Kweb projections in box-layout order. It does not store a second durable copy
of those node bodies as an ordinary tool-result box.

If all relevant boxes were already current, the concise result is:

LoadNode completed. The shared Kweb boxes were already current.

This keeps one canonical stateful representation per Kweb logical slot while
still giving the immediate tool call a useful response.


Choices that were considered and rejected
-----------------------------------------

Repeating ID and name in the header:
Rejected because the body already carries both and the repetition occurs in
every representation of every full node.

Showing Chatend owner in Kweb headers:
Rejected because Chatend control ownership and Kweb resource ownership are
different concepts. The Kweb owner belongs in node data.

Removing owners from all Chatend headers:
Rejected because the concise form is a Kweb presentation choice, while other
box types may rely on the generic owner label.

One recent box per loaded node or role:
Rejected because it multiplies boxes and makes a connection's unique placement
depend on traversal and role precedence.

Promoting a recent prefix to active full nodes:
Rejected because recency is navigation information, not an implicit authority
to spend full-context capacity.

Giving loaded, fixed, and staged nodes different body schemas:
Rejected because the underlying node data has one meaning. The box kind is
enough to explain why it is present.

Emitting a Kweb-specific update notice:
Rejected because moving updated state through history is a generic Chatend
responsibility.

Putting Chatend persistence inside the context library:
Rejected because it would couple Kweb projection policy to one history engine
and make stable slot reconciliation have two owners.


Regression checklist
--------------------

Before changing context rendering, verify all of the following:

* each explicitly loaded node has exactly one loaded full box;
* each distinct fixed connection has one fixed full box unless loaded wins;
* staged creates have staged full boxes and staged updates retain their role;
* all three full-node kinds use the same body formatter;
* no active-node role or active-connection field exists;
* there is exactly one recent-connections box;
* recent entries are globally deduplicated and include name plus description;
* Kweb full headers do not repeat node ID, name, or Chatend owner;
* Kweb owner is present in the node body;
* logical slots preserve box identity across revisions;
* every superseded earlier occurrence renders exactly "[box updated]";
* no Kweb-specific update-notice boxes are created; and
* LoadNode does not duplicate shared state in another durable result box.

The focused library tests should assert exact strings for the loaded body,
concise header, recent-entry format, and update marker. The workspace tests
should also cover Kweb layout ordering and exact LoadNode changed-box results.
